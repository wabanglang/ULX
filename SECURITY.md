# Security and Responsible Disclosure

ULX may eventually include parsers, validators, benchmark runners, converters, or other tooling. Security reports concerning public ULX code should be disclosed responsibly before public exploitation details are posted.

## Reportable issues

Examples include:

- code execution or injection vulnerabilities;
- unsafe parsing behavior;
- path traversal or file handling defects;
- benchmark tooling that leaks private source material;
- provenance or integrity failures that allow silent tampering;
- vulnerabilities in released ULX tooling that materially affect users.

## Not a security report

Disagreement with ULX research claims, benchmark design, terminology, or experimental conclusions should normally be filed as a regular issue or research critique rather than as a vulnerability.

## Private implementation boundary

The public repository intentionally excludes unreleased proprietary implementation details. Please do not publish material obtained through unauthorized access to private systems, credentials, accounts, or data.

## Disclosure principle

Provide the minimum information needed to reproduce and repair a security defect, and avoid exposing unrelated private information.
